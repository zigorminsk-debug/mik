# Подпись Android-приложения

Приложение подписывается **постоянным** ключом: только он позволяет ставить новые версии
поверх ранее установленных (иначе Android потребует удалить приложение и потерять данные).

## Где лежит ключ

Ключ — файл PKCS12 (`mik-release.p12`, RSA-2048, самоподписанный сертификат, срок 100 лет).
Хранится **только в секретах GitHub** и подставляется в сборку через GitHub Actions.
В репозитории, в ветках и в артефактах сборки ключа нет.

> ### Важно
> Ранняя версия проекта держала ключ в публичной ветке `signing-key`. Так делать нельзя:
> репозиторий публичный, значит ключ был скомпрометирован. Ветка удалена, ключ **ротирован**,
> и сборка теперь читает его исключительно из секретов репозитория.

CI получает ключ так:

1. **Секреты репозитория** — единственный источник:
   `Settings → Secrets and variables → Actions → New repository secret`

   | Секрет | Значение |
   |---|---|
   | `ANDROID_KEYSTORE_BASE64` | base64 содержимого `.p12` (одной строкой) |
   | `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
   | `ANDROID_KEY_ALIAS` | alias ключа (`mikacademy`) |
   | `ANDROID_KEY_PASSWORD` | пароль ключа (в PKCS12 обычно равен паролю хранилища) |

2. Если секреты не заданы — собирается только debug-APK, шаг release пропускается
   с предупреждением в логе сборки. Неподписанный APK никогда не публикуется как релиз.

Секреты доступны в workflow для `push`, `workflow_dispatch` и тегов `v*`.
Для pull-request из форков секреты не выдаются, поэтому release-сборка там пропускается.

## Отладочная сборка (`com.mikacademy.app.debug`)

Отладочные сборки подписываются **постоянным отладочным ключом**, который лежит
в репозитории: `android/keystore/mik-debug.p12` + `mik-debug.properties`.

Это сделано намеренно:

* отладочный ключ **ничего не защищает** — доступ к нему есть у всех, кто видит репозиторий;
* без постоянного ключа каждая сборка в CI подписывалась бы случайным отладочным
  ключом, и новая сборка не устанавливалась бы поверх предыдущей
  («Приложение не установлено, так как оно конфликтует с другим пакетом»);
* постоянство подписи позволяет спокойно обновлять отладочную версию на телефоне.

Релизный ключ при этом остаётся в секретах репозитория и в репозиторий не попадает.

## Как добавить ключ в секреты (разово)

```bash
# 1. Получить base64 ключа (файл mik-release.p12)
base64 -w0 android/keystore/mik-release.p12

# 2. Создать секреты (нужен токен с правом Actions: Secrets)
gh secret set ANDROID_KEYSTORE_BASE64 < mik-release.p12.b64
gh secret set ANDROID_KEYSTORE_PASSWORD --body 'пароль'
gh secret set ANDROID_KEY_ALIAS --body 'mikacademy'
gh secret set ANDROID_KEY_PASSWORD --body 'пароль'
```

Проверка:

```bash
gh secret list
```

Если секретов ещё нет, выполните шаг вручную в интерфейсе GitHub:
`Settings → Secrets and variables → Actions → New repository secret` — по одному секрету
на строку таблицы выше.

## Как восстановить ключ из секретов

```bash
echo "$ANDROID_KEYSTORE_BASE64" | base64 -d > mik-release.p12
keytool -list -v -keystore mik-release.p12 -alias mikacademy -storepass "$ANDROID_KEYSTORE_PASSWORD"
```

## Как создать новый ключ (если старый утерян)

```bash
python3 -m venv .venv && .venv/bin/pip install cryptography
.venv/bin/python scripts/make-keystore.py
# → android/keystore/mik-release.p12 и android/keystore/mik-release.p12.b64
```

Скрипт пишет реквизиты в `.secrets/keystore.txt` (папка вне git).
Дальше — залить base64 в секрет `ANDROID_KEYSTORE_BASE64` и обновить пароль/alias.

> ⚠️ Новый ключ = новая «личность» приложения. Установка поверх старой версии
> невозможна: придётся удалить приложение. Старый ключ терять нельзя.

## Проверка подписи собранного APK

В CI это делает шаг «Проверить подпись и собрать артефакты»:

```bash
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --verbose --print-certs app-release.apk
```

В выводе должен быть сертификат с CN `MikroTik Academy Release` и теми же отпечатками,
что и у исходного ключа.

## Отпечаток текущего ключа

Сертификат: `CN=MikroTik Academy Release, O=MikroTik Academy, C=BY`
Алгоритм: RSA-2048, срок действия — до 2126 года.
Точный SHA-256 можно посмотреть командой выше.

Ротация: текущий ключ создан заново после того, как временный ключ оказался в публичной
ветке. Прежние сборки, подписанные старым ключом, обновляться новым не будут — поэтому
первый релиз с новым ключом нужно ставить поверх версии, собранной этим же ключом.
